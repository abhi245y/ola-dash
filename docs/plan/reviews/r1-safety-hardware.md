# PLAN.md review: safety and hardware realism

Ranked, most severe first. Paths: SDK = /home/arl/Documents/code/ola-re/ola-dash-sdk, REA = /home/arl/Documents/code/ola-re/ola-s1-rea/docs.

## 1. [Critical, blocks E0.S5 / E2.S3 / E4] Theme code can switch off host telltales, alert cards and the lock screen
- Problem: fixed constraint 1 ("themes style but never hide" the overlay) is false for the current host, and the plan ships a store and one-tap switcher on top of it. Two holes: (a) a theme may assign contract `in` properties, and the overlay reads them directly; (b) a theme may `import` the host's own overlay/unlock files and write `HostState`, `OverlayConfig`, `LockConfig` (bypassing the Rust contrast checks).
- Evidence (reproduced today with the SDK's own `sim --check`, which E4.S2.T3 CI runs; both themes passed, exit 0): a theme with `Timer { triggered => { Vehicle.left-indicator = false; } }` rendered at t=13 has telltale slot 0 at (10,10,10) vs (92,255,157) for `themes/minimal`; a theme importing `host/ui/overlay.slint` and writing `HostState.alert-code = 0; HostState.auth-phase = 4` renders no side-stand card with `--alert 3` and no keypad with `--state locked`. Same code path on device: `sim/src/main.rs:36` includes `host/src/theme_root.rs`; the overlay reads `Vehicle.*` in `host/ui/overlay.slint:139-149`; `theme_entry` validates only the `entry` field (`host/src/lib.rs:304`), no import path inside `.slint` files is checked; E4.S3.T2's "no `..`" rule covers zip entry names only. On device the import is the relative string `"../../host/overlay.slint"` from `files/themes/<id>/`.
- Change: add **E0.S6 Theme sandbox** (M1, blocking E0.S5, E2.S3, E4): (1) import guard on the probe compile (`lib.rs:322-325`) via `Compiler::set_file_loader` (exists: slint-interpreter 1.18.1 `api.rs:792`): serve only `vehicle.slint` and files under the theme folder, refuse everything else so the probe fails and the loader falls back; (2) the overlay and `UnlockScreen` read host-private mirrors of the 8 telltale inputs, clock and battery written from Rust next to `Vehicle.*`, so a theme write only breaks the theme's own display (mirrors are private only because of (1)); (3) the two adversarial themes become negative tests in `check-themes` and store CI. Do not rely on a regex for assignments: a two-way binding `property <bool> x <=> Vehicle.left-indicator;` writes through without an `=` on the global.

## 2. [High, blocks E5.S1 as written] The recovery watchdog cannot do what T3 says from an app, and would false-trigger
- Problem: a non-root APK cannot `pm enable` or `cmd package set-home-activity` (the restore sequence is `host/test/hmi-swap.sh stock`). "Three crashes within 10 minutes" fires on normal use. The heartbeat stops when the display sleeps. A hung Slint loop passes a Java-written heartbeat.
- Evidence: root exists only through the diagnostic daemon on `[::1]:50005` (REA 17-gen1-root-helper: app UID 10038 reached it; design has no resident polling loop; fails closed if daemon/mode unsupported). Ride log `docs/ride-log-2026-10-30.md`: "Each power-button wake recreates the activity, so logs split into a ~1 s session plus the real one". REA 13-gen1-root-adb: locked scooter sits at `mWakefulness=Asleep`, display OFF, for hours. Stakes: with `hmiclient` disabled the host keypad is the only passcode entry (REA 07: keypad is Kanzi inside hmiclient; REA 06: the only other unlock path is phone->cloud->TCU), so a dead host is a stranded rider until stock is restored.
- Change: E5.S1.T2: heartbeat written by a `slint::Timer` on the UI thread every 5 s with `elapsedRealtime` (proves the event loop is alive), plus a Java tick; T3: watchdog is a separate APK/process that acts only through `[::1]:50005`, runs on `BOOT_COMPLETED` and on an explicit request from the host, treats "failure" as (display interactive per `dumpsys power`) AND (no UI heartbeat for M-start x 3 measured after a cold reboot) OR (>= 3 abnormal process exits in 10 min: no clean `onDestroy` marker and a new pid; activity recreation in the same pid is not a crash); restore sequence = exactly `hmi-swap.sh stock`; fail closed and log if the daemon or `id -u 0` is unavailable. State the stranded-rider consequence in safety.md.

## 3. [High] A theme that compiles but crashes at render loops forever; E0.S5's AC covers compile failures only
- Problem: "a broken theme cannot replace a working one" holds for compile errors; a theme that OOMs or panics on first frame (huge `for`, a 2 MB SVG that resvg chokes on) crash-loops the home app, and the fallback tiers (`lib.rs:345-356`) never engage because the crash is after `create()`.
- Change: E0.S5.T5: in `MainActivity.onCreate` before `super.onCreate` (Slint init happens inside it, `MainActivity.java:61-67`): if the previous start with theme X never wrote a "first frame + 10 s" marker, twice in a row, set `files/themes/active` to `default` and mark X bad in settings. No root needed; this is the layer under the watchdog. AC: a theme that panics on first frame is reverted within two starts without a laptop.

## 4. [High] Plugins are ordinary APKs with the same vehicle access as the host; "display-only" is an API property, not a sandbox
- Evidence: the host binds the stock parser with plain `bindService` and no permission (`VehicleBridge.java:237-238`) and reaches `sendCommandToScooter` the same way (`:217`). Any installed plugin can do likewise; nothing in E4.S1.T2 / E4.S4.T1 looks for it.
- Change: E4.S1.T2 / E4.S2.T3: store CI rejects a plugin APK whose dex strings or manifest reference `com.olaelectric.vehicleparser`, `com.olaelectric.vehicleinterface`, `ICommanderService`, or that requests `SYSTEM_ALERT_WINDOW`, `BIND_ACCESSIBILITY_SERVICE`, `BIND_NOTIFICATION_LISTENER_SERVICE`, `REQUEST_INSTALL_PACKAGES`; safety.md gains the sentence "an installed plugin is an ordinary Android app; the plugin API is display-only, the APK is not sandboxed by the host".

## 5. [High] Stale vehicle values are shown as live, and E0.S5 `LAST` makes it a feature
- Evidence: `onServiceDisconnected`/`onBindingDied` (`VehicleBridge.java:402-421`) reset the trunk-gate fields but push nothing to the UI; the last speed stays on every theme and on the planned dash bar for the 3 s rebind or forever if the parser is dead. The `LAST` table (E0.S5.T1) re-applies the same stale values to a new root.
- Change: E0.S5.T1: `LAST` carries an age; add host-owned `HostState.data-stale` set on disconnect/binding-died and when no vehicle callback arrived for N s while `state == drive`, cleared on `subscribed`; the strip shows a host "NO DATA" badge and the dash bar shows `--` for speed while stale. AC for E1.S5.T4: kill the parser with the bar up, speed must blank within one rebind interval.

## 6. [High] Nothing returns to the dash when the scooter starts moving with a non-AA app in front
- Problem: E1.S4.T3 gates *launching*; E0.S3.T3 closes only host screens. Android Settings (E1.S3.T3) or any launched app opened at a light stays in front at 40 km/h with only the 48 px bar.
- Evidence: Android 10 blocks activity starts from the background; the only exemption the host can claim is the granted `SYSTEM_ALERT_WINDOW` appop. Knowing which package is in front needs `PACKAGE_USAGE_STATS` (appop) on API 29; the host otherwise only knows its own activity is paused.
- Change: E0.S3.T3: "when `parked` turns false and the resumed package is not the AA receiver, the host brings itself to front"; E5.S2.T4 grants `PACKAGE_USAGE_STATS`; E1.S5.T4 matrix adds "Settings in front, then DRIVE: host returns within 1 s" and verifies the SAW background-start exemption on this build. Same mechanism carries E1.S5.T2 and E6.S2.T3; the plan should name the Android 10 restriction once.

## 7. [Medium] E1.S5 AC overclaims what a TYPE_APPLICATION_OVERLAY window can guarantee
- Problem: "the bar can not be dismissed by the foreground app" is false for any other SAW holder (the owner granting it, a plugin, the receiver) which draws later and above, and for system windows (ANR, permission and PackageInstaller dialogs). The bar also sits above the host's own activity when the host is in front. If the host process is LMK-killed while AA is in front, the bar dies silently.
- Change: AC: "a foreground app without `SYSTEM_ALERT_WINDOW` cannot cover it; the installer grants SAW only to the host and the store refuses APKs that request it". T1: hide the bar in `onResume`, show in `onPause`; hold a foreground service (notification) while another app is in front. T2: for critical alerts, expand the bar window itself to full screen (no activity start needed) and only then try to bring the activity forward. Keep-alive is blind while another app is in front (`VehicleBridge.java:107`); try `FLAG_WATCH_OUTSIDE_TOUCH` on the bar to feed `TOUCHED` and verify delivery.

## 8. [Medium] Parked gate reads "unknown" as unlocked and may never become true after a cold start
- Evidence: `!locked` as a boolean: `Vehicle.locked` defaults false (`contract/vehicle.slint:82`) and BCM lock state is only set on a callback; TrunkGate already uses tri-state `Boolean.TRUE.equals(bcmUnlocked)` (`TrunkGate.java:30`, `realBcmUnlocked` `VehicleBridge.java:113`). "Speed known" depends on parser replay at subscribe, which the code records as partial (`VehicleBridge.java:425-426`): if 0 km/h is not replayed while parked, settings are unreachable until the scooter has moved. `state in {charging}` with `!locked` is dead for the common charging-while-locked case.
- Change: E0.S3.T1: `ParkGate` = `TrunkGate.refusal` minus trunk and rate limit (reuse, one gate), tri-state lock, fail closed; E0.S4 measures which fields the parser replays on subscribe and the plan records the "unreachable until first motion" risk and its mitigation; decide and state whether charging-while-locked is parked.

## 9. [Medium] Hot-swap blocks the UI thread and must re-wire the keypad, or the rider is locked out
- Evidence: `build_root` compiles with `spin_on` on the UI thread (`lib.rs:324,329`); `ComponentDefinition` is `Rc`-based, so a worker-thread compile is not a given. During M-compile no `flush`, no blink, no alert card. `wire()` (`lib.rs:415-469`) and `theme_root::bind` are per-instance; an unwired `unlock-key` on the new root leaves no working passcode keypad (stock keypad disabled). Slint's Android backend owns one surface; "show the new root, then drop the old" is unverified for a second `Window` component.
- Change: E0.S5.T2: switch only while `parked && alert-code == 0 && auth-phase >= 4`; re-run `wire()` and `theme_root::bind()` on the new instance; re-check the gate right after the swap; AC adds "keypad, trunk and media callbacks work after the swap" (extend `host/test/unlock-preview.rs`). T3: state that the strip freezes for M-compile. E4.S3.T2's probe compile has the same cost: parked-only, or verify `Compiler: Send` before promising a worker thread.

## 10. [Medium] Owner PIN must not share the unlock keypad path; cooldown must not depend on the clock
- Evidence: the only keypad route today is `unlock-key` -> `MainActivity.onUnlockKey` -> `UnlockController` -> stock profile service (`lib.rs:418-432`, `UnlockController.java:102-167`), whose 5-attempt / 5-minute budget is vehicle-side (REA 06). Device clock validity is unverified (see 16).
- Change: E1.S6.T2: separate callback, screen refused while `auth-phase < 4`, attempts persisted, cooldown on `elapsedRealtime` with a reboot counting as cooldown start; a PIN screen never covers the host lock screen (host screens are drawn between `Dash` and `HostOverlay`).

## 11. [Medium] Hub button in the telltale strip: too short, and tappable during alerts and while locked
- Evidence: strip is 48 px (`OverlayTokens.strip-h`, `overlay.slint:15`) vs the SDK's 64 px touch minimum (`docs/themes.md:158`); with labels the strip has 184 px free horizontally, 104 px vertically. The strip is drawn above the alert scrim and above the lock screen (`overlay.slint:310, 348, 363`), so a strip button is live during a fall alert and while locked.
- Change: E1.S1.T2: button is 64 px wide by strip height, at the far end of the strip, never displaces or shrinks a telltale; hidden when `!parked || alert-code != 0 || auth-phase < 4`; add to the host-fixed list in safety.md.

## 12. [Medium] Android Auto may be launched while riding; the bar's default edge covers AA's own bar
- Evidence: `Actions.open-android-auto` calls `launch()` with no gate (`lib.rs:434-437`). AA's home/mic/apps bar sits at the bottom of the projected image; the dash bar default is bottom 48 px (E1.S5.T3).
- Change: E1.S4.T3 / E6.S2.T1: the exception is *staying* in front, not launching; gate the theme callback, launcher tile and E6.S2.T3 auto-launch on `parked`. E6.S2.T2: AA-mode bar edge defaults to top until E6.S1.T3 answers the margin question.

## 13. [Medium] Signed store index can be replayed to downgrade the host
- Evidence: E4.S2.T2 signs `index.json`; E5.S3 updates the host from it; nothing in the signed payload is monotonic, so an attacker on the Wi-Fi path replays an older index and an older host APK.
- Change: E4.S2.T1: signed payload carries `seq`; host refuses `seq` lower than the last accepted and a host `versionCode` lower than installed; record "no key rotation in 1.0" in the decision log.

## 14. [Medium] Screen-on and RAM assumptions
- Evidence: the stock HMI declares `keepScreenOn` (REA 07-hmi-ui:20); the host manifest sets nothing (`host/AndroidManifest.xml`). The 0.78 GiB free sample was taken with the stock HMI mapped (~410 MB, REA 07); M-ram and M-aa are not comparable to it.
- Change: E1.S5.T4 matrix: "ride longer than the Android screen timeout, host in front and AA in front"; add `FLAG_KEEP_SCREEN_ON` while `state == drive` and verify (the vehicle may manage display power itself). E0.S4.T2: measure PSS with `hmiclient` disabled and note the baseline.

## 15. [Low] Brightness via `WRITE_SETTINGS` is unverified and may be a vehicle-side setting
- Evidence: the vehicle interface carries `setScooterBrightnessLevel` / `onBrightnessLevelChanged` (`sdk/vehicle-interface/SPEC.md:189,289`); the panel may not follow `SCREEN_BRIGHTNESS`.
- Change: E1.S3.T1: brightness is a measurement task; if only the vehicle path works, decide in the D-log whether a display-brightness request counts as a vehicle command under safety.md.

## 16. [Low] Night mode by clock with an unverified clock
- Evidence: no document establishes RTC backup or network time on the Gen 1 head unit; AHO (headlamp always on, Indian two-wheelers) makes `Vehicle.headlight` useless for day/night.
- Change: E2.S2.T1: `auto` falls back to the manual setting when the year is implausible or `AUTO_TIME` is off; E0.S4 adds "`date` right after a cold boot without network".

## 17. [Low] Unspecified failure handling
- `settings.json` parse failure: rename to `.bad`, start with defaults, log, never crash (E1.S3.T2). E1.S1.T3 "hardware back": the panel has no Back key (red button is power/lock; `keyevent 3` is adb-only, REA 04, 07); drop it or mark adb-only. E5.S2.T2 "scooter parked", "battery above 30 %": the installer has no vehicle data source; name one (host calls log via adb, or an owner confirmation). E4.S4.T2: verify `com.android.packageinstaller` exists on this build before relying on the confirmation UI; the self-update kills the home app mid-install, so the watchdog must treat that restart as clean. E1.S5.T1 "plain Android Views" duplicates telltale semantics: feed the bar from the same Java state as `pushAlerts` (`VehicleBridge.java:495-514`) and share the colour constants.

## Verdict
Two items block the plan as written: the theme sandbox hole (1) makes fixed constraint 1 false today and the store would distribute it, and the watchdog (2) cannot act from an app and would restore stock while the owner sleeps; with the stock HMI disabled a dead host is also a lost passcode keypad, which the plan never says.
Items 3-6 are missing failure modes that turn a bad theme, a dead parser, or a stray app into a riding-time hazard; each is a small text change plus one AC.
Everything else is wording or a measurement task; the plan's "measure first" discipline is right, it just needs the Android 10 restrictions, the single-UI-thread compile, and the no-Back, no-keepScreenOn, no-root-from-app facts written into the stories that depend on them.
